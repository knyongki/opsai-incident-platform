# OpsAI API reference

The API listens on `http://127.0.0.1:8080` by default (`HTTP_ADDRESS`). All
application responses use `Content-Type: application/json` and one of two envelopes:

```json
{ "data": { } }
{ "error": { "code": "VALIDATION_ERROR", "message": "..." } }
```

| Error code | HTTP | Meaning |
| --- | --- | --- |
| `VALIDATION_ERROR` | 400 | Malformed JSON, unknown fields, wrong types, invalid IDs or values |
| `NOT_FOUND` | 404 | Unknown path or missing resource |
| `CONFLICT` | 409 | The change conflicts with stored data, such as deleting a device that has incidents |
| `DATABASE_UNAVAILABLE` | 503 | Readiness check could not reach PostgreSQL |
| `INTERNAL_ERROR` | 500 | Unexpected failure; database error text is never returned |

Unsupported methods return 405 with an `Allow` header. Paths match exactly
(`/health/` is not `/health`). IDs are standard hyphenated UUIDs generated by
the server; clients cannot set IDs, statuses, or server timestamps. Timestamps
are returned in UTC.

To try these requests, use the [Postman quickstart](Postman-Quickstart.md) or
the PowerShell examples below.

## System

| Method and path | Response |
| --- | --- |
| `GET /health` | 200 `{"data":{"status":"ok"}}` while the process serves requests |
| `GET /ready` | 200 `{"data":{"status":"ready"}}`, or 503 `DATABASE_UNAVAILABLE` |

`/ready` pings PostgreSQL with a two-second deadline on every request. It checks
connectivity, not schema or migration state. Both routes also support HEAD
without a body (`Allow: GET, HEAD`). Malformed HTTP rejected before routing uses
Go's protocol-level responses.

```powershell
curl.exe -i http://127.0.0.1:8080/health
curl.exe -i http://127.0.0.1:8080/ready
```

## Devices

| Method | Path | Success |
| --- | --- | --- |
| POST | `/api/v1/devices` | 201, device in `data`, and `Location` header |
| GET | `/api/v1/devices` | 200, array in `data` (empty array when none) |
| GET | `/api/v1/devices/{id}` | 200, device in `data` |
| PATCH | `/api/v1/devices/{id}` | 200, updated device in `data` |
| DELETE | `/api/v1/devices/{id}` | 204, no response body |

```powershell
$base = 'http://127.0.0.1:8080/api/v1/devices'
$body = @{
    name = 'AMR-07'
    type = 'amr'
    location = 'Assembly line 1'
    metadata = @{ manufacturer = 'Example' }
} | ConvertTo-Json -Depth 10
$created = Invoke-RestMethod -Method Post -Uri $base -ContentType 'application/json' -Body $body
$deviceId = $created.data.id
Invoke-RestMethod -Method Get -Uri $base
Invoke-RestMethod -Method Get -Uri "$base/$deviceId"
$patch = @{ status = 'online'; location = $null } | ConvertTo-Json
Invoke-RestMethod -Method Patch -Uri "$base/$deviceId" -ContentType 'application/json' -Body $patch
Invoke-WebRequest -Method Delete -Uri "$base/$deviceId" -UseBasicParsing
```

| Field | Contract |
| --- | --- |
| `name` | Required on create, nonblank, at most 200 characters |
| `type` | Required on create, nonblank, at most 50 characters |
| `status` | Optional nonblank text, at most 50 characters; defaults to `unknown` |
| `location` | Nullable text, at most 500 characters |
| `metadata` | JSON object up to 16 KiB; defaults to `{}` |

Suggested types include `amr`, `conveyor`, `plc`, `robot`, and `other`; other
nonblank values are accepted. NUL characters are rejected, request bodies are
limited to 64 KiB, and duplicate device names are allowed. These limits are
application rules; the database columns are plain TEXT.

PATCH requires at least one field, preserves omitted fields, and accepts null only
for `location`. Supplied metadata replaces the whole object. Each update is a
single SQL statement, so concurrent changes to different fields do not overwrite
each other; changes to the same field keep the last update. Lists are ordered by
creation time, then ID, without pagination. Deleting a device that is referenced
by an incident returns 409 `CONFLICT`. Each operation has a five-second deadline.

## Incidents

| Method and path | Response |
| --- | --- |
| `POST /api/v1/incidents` | 202 `{"data":{"id":"…","status":"open","analysis_status":"queued"}}` |
| `GET /api/v1/incidents` | 200 page of incident summaries |
| `GET /api/v1/incidents/{id}` | 200 complete incident, including `analysis` |

The collection route allows `GET, POST`; detail allows `GET`. Each operation has
a five-second deadline. Reads never modify incidents or jobs.

### Create an incident

`POST /api/v1/incidents` stores the incident and its analysis job in one
PostgreSQL transaction: both are saved or neither is, and 202 is returned only
after the commit. `queued` means the job is stored and waiting for a worker.
Repeating the request creates another incident and job (no idempotency key).

| Field | Contract |
| --- | --- |
| `device_id` | Required UUID of an existing device |
| `title` | Required, nonblank, at most 200 Unicode characters |
| `description` | Required, nonblank, at most 10,000 characters |
| `severity` | Required: `low`, `medium`, `high`, or `critical` |
| `alarm_code` | Optional/null; at most 100 characters |
| `raw_logs` | Optional (defaults to `[]`); at most 100 strings of 1,000 characters each; null array/entries rejected |
| `occurred_at` | Optional/null; RFC3339 timestamp with offset; normalized to UTC; future dates allowed |

NUL and invalid UTF-8 text, unknown fields, malformed or multiple JSON values, and
bodies larger than 256 KiB return 400 `VALIDATION_ERROR`. A missing device returns
404 `NOT_FOUND`. Incident records persist; there is no delete endpoint.

Storage (migration `00002`): severity and status check constraints, a nonnegative
attempt count, device and incident foreign keys, one job per incident, a
device-reference index, and an index of pending jobs by availability time. Worker
retries update the same job row; reanalysis history is not modeled.

```powershell
$base = 'http://127.0.0.1:8080'
$deviceBody = @{ name = 'Demo incident device'; type = 'amr' } | ConvertTo-Json
$demoDevice = Invoke-RestMethod -Method Post -Uri "$base/api/v1/devices" -ContentType 'application/json' -Body $deviceBody
$incidentBody = @{
    device_id = $demoDevice.data.id
    title = 'Demo docking failure'
    description = 'Synthetic incident for local verification.'
    severity = 'high'
    raw_logs = @('Synthetic docking log')
    occurred_at = '2026-09-14T09:30:00Z'
} | ConvertTo-Json
$response = Invoke-WebRequest -UseBasicParsing -Method Post -Uri "$base/api/v1/incidents" -ContentType 'application/json' -Body $incidentBody
$response.StatusCode # 202
$incidentId = ($response.Content | ConvertFrom-Json).data.id
```

### List incidents

| Parameter | Contract |
| --- | --- |
| `limit` | Decimal integer, default 20, range 1-100 |
| `cursor` | Opaque `next_cursor` from the preceding page; omit for the first page |
| `device_id` | Exact hyphenated UUID; UUID letter case is normalized |
| `status` | Exact `open`, `analyzing`, `analyzed`, `analysis_failed`, or `resolved` |
| `severity` | Exact `low`, `medium`, `high`, or `critical` |
| `alarm_code` | Exact case-sensitive text, at most 100 characters; NUL/invalid UTF-8 rejected |

The empty response is
`{"data":{"items":[],"page":{"next_cursor":null,"has_more":false}}}`. Filters
combine with AND. Empty values are invalid except `alarm_code=`, which matches a
stored empty string, not NULL; omit `alarm_code` to include all values. Malformed
cursors, invalid filters or limits, duplicate or unknown parameters, and malformed
query encoding return 400. Detail accepts no query parameters.

Items contain only `id`, `device_id`, `title`, `alarm_code`, `severity`, `status`,
`analysis_status`, `occurred_at`, `created_at`, and `updated_at`. They never include
`description`, `raw_logs`, or `analysis`.

**Pagination.** Rows are ordered by `created_at DESC, id DESC`. Each query fetches
`limit + 1` rows; the extra row sets `has_more`, and `next_cursor` then represents
the last returned row (otherwise it is null). Later pages use the strict tuple
boundary `(created_at, id) < (cursor timestamp, cursor UUID)` with no offset, so
equal timestamps never cause skipped or duplicated rows.

The cursor is versioned canonical JSON in unpadded base64url, holding the
timestamp, UUID, and a SHA-256 of the normalized filters. Treat it as opaque and
resend the same filters; changed or omitted filters return 400. The page size may
change. The cursor is not signed and is not an authorization token. It is not a
snapshot: rows inserted ahead of the boundary require starting again from the
first page, and changing filter fields can change page membership.

```powershell
$filters = "device_id=$($demoDevice.data.id)&status=open&severity=high"
$firstPage = Invoke-RestMethod "$base/api/v1/incidents?limit=1&$filters"
$firstPage.data.items
if ($firstPage.data.page.has_more) {
    $cursor = [Uri]::EscapeDataString($firstPage.data.page.next_cursor)
    Invoke-RestMethod "$base/api/v1/incidents?limit=1&$filters&cursor=$cursor"
}
```

### Incident detail

```powershell
Invoke-RestMethod "$base/api/v1/incidents/$incidentId"
```

Detail returns the summary fields plus `description`, `raw_logs`, `resolved_at`,
and `analysis`. `alarm_code`, `occurred_at`, and `resolved_at` are JSON null when
absent; `raw_logs` is always an array. An invalid UUID returns 400 and a
nonexistent incident returns 404 `NOT_FOUND`.

`analysis_status` comes from the incident's job: `pending` is shown as `queued`;
`running`, `completed`, and `failed` keep their names. Job IDs, attempt counts,
lock timestamps, and internal error codes are never exposed. A missing or invalid
job is a storage invariant failure and returns 500 `INTERNAL_ERROR` rather than
hiding the incident.

### Analysis

`analysis` is `null` until a validated result is stored: for queued, running, and
failed jobs, and for completed jobs that predate stored results. Otherwise:

```json
{
  "id": "UUID",
  "schema_version": 1,
  "source": "fake",
  "created_at": "UTC timestamp",
  "result": { "summary": "...", "primary_suspected_cause": "...",
              "contributing_factors": [], "observed_conditions": ["..."],
              "recommended_actions": [], "safety_notes": ["..."],
              "confidence": 0, "evidence": [{ "source_id": "incident UUID", "claim": "..." }] }
}
```

`source: "fake"` marks deterministic test output from the fake analyzer: no
diagnosis was performed and confidence is 0. The result fields are defined in the
[analysis contract](Worker-and-Analysis.md#analysis-result-contract). Stored JSON
is decoded again with the strict validator before it is returned. An unsupported
version or source, a malformed result, evidence for another incident, or a result
attached to a non-completed job returns 500 `INTERNAL_ERROR`; unvalidated JSON is
never returned. The incident, job status, and analysis are read in one SQL
statement, so a concurrent completion cannot produce a mixed response.

The sqlc queries `ListIncidents` and `GetIncident` use left joins on existing
indexes, which are sufficient for correctness. Large datasets may need a measured
index improvement; load testing has not been done.
